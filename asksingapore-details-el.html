AI Lab / Live · Domain Προς Πώληση

AskSingapore.ai

A live, single-page AI travel guide for Singapore — real answers streamed word-by-word from Agnes AI through a serverless edge proxy. A standalone concept site that shows what the asksingapore.ai domain can become; the domain itself is available for acquisition.

TL;DR

A one-screen marketing site with a real LLM chat at its centre: visitors ask anything about Singapore — hawker food, hotels, getting around — and get a live, streamed answer. No framework, no build step, no server to patch; the whole thing is one HTML file plus one edge function.

  • What — live AI travel chat + domain showcase for asksingapore.ai
  • Stack — Cloudflare Pages + Pages Functions · Agnes AI (agnes-2.5-flash, OpenAI-compatible, SSE streaming) · Apps Script + Google Sheets (anonymous Q&A log)
  • Edge-native — vanilla HTML/CSS/JS, zero build; push to main → live in ~30 seconds, instant rollback
  • Relation to AskSantorini — standalone; not connected to the AskSantorini engine
  • Status — live at asksingapore.ai; the domain is for sale

Overview

AskSingapore.ai is the second destination in the studio’s “Ask” domain network. Where the flagship, AskSantorini.ai, is a full concierge platform with a booking engine behind it, AskSingapore is deliberately minimal: a single premium page whose centrepiece is a working AI guide. A visitor types a question and real artificial intelligence answers — Agnes AI, Singapore’s own homegrown model, a deliberate pairing for a Singapore site.

The page exists to prove a point about the domain: instead of a parked “for sale” placeholder, a buyer lands on a living demonstration of what the name can carry. The chat is the page’s only network call (plus a small live weather line under the Singapore clock); everything else — the adaptive visual themes, the decorations, the copy — is local and static.

It shares an idea with AskSantorini, not an implementation: there are no shared Workers, no shared runtime, no shared codebase. It is a self-contained concept site, and it is presented as exactly that.

Built and maintained solo as an AI-assisted product: I own the architecture and the decisions; an AI coding agent handles execution under a strategy-first, gated workflow with reviewable diffs and rollback-first deploys.

Tech Stack

Frontend

  • One HTML file — markup, CSS and the chat client all live in index.html; no framework, no bundler, no build step
  • Streamed reveal — the client parses the SSE stream and reveals real tokens word-by-word at a reading cadence (45 ms/word, slower fade under prefers-reduced-motion)
  • Local touches — a live SGT clock and a live weather line (Open-Meteo, keyless, fetched client-side; hidden entirely on failure — no fake fallback)

Backend (serverless proxy)

  • A single Cloudflare Pages Function — POST /api/chat, same origin as the page, so no CORS surface
  • Validates input (message ≤600 chars; history sanitized and capped at 10 turns), rate-limits, then proxies Agnes AI (agnes-2.5-flash, OpenAI-compatible /v1/chat/completions, stream: true, 50s timeout) and passes the SSE straight through
  • The AGNES_API_KEY secret lives only in the Cloudflare dashboard — it never reaches the browser

Logging & analytics (anonymous)

  • The function tees the stream: while tokens flow to the visitor, it reassembles the full answer and fire-and-forgets {question, answer} to an Apps Script webhook
  • Rows land in a Google Sheet (Timestamp (SGT) | Question | Answer) — no IPs, no identifiers, and the page says so
  • The log doubles as a quality tool (see what the model answers) and sales evidence (see what the world asks Singapore)

Hosting

  • Cloudflare Pages, git-connected: merge to main → live in ~30 seconds; rollback is one revert or one dashboard click

Architecture

The whole system is a page, a proxy, and a log — the proxy exists so the model key stays locked inside Cloudflare:

[Visitor question]
      │
      ▼
(Pages Function /api/chat) ──> validate + rate-limit
      │
      ▼
Agnes AI — agnes-2.5-flash · stream: true · Bearer AGNES_API_KEY
      │
      ├──> SSE pass-through ──> browser (word-by-word reveal)
      │
      └──> tee: reassemble answer ──> Apps Script /exec ──> Google Sheet
           (anonymous log — no IPs, no identifiers)

Errors are mapped, never leaked: bad input → 400, rate-limited or upstream saturation → 429, upstream failure → 502, missing key → 503, timeout → 504. The frontend renders each as a calm, honest line — “try again in a moment” — and a partial answer that gets cut mid-stream is visibly marked before the error line, never silently patched over.

Key Features

  • Live streamed answers — real model tokens in their original cadence, paced for reading; no canned responses are ever presented as live output.
  • Answers in the visitor’s language — ask in any language, the guide replies in kind, capped at a concise ~150 words.
  • Venue hallucination guard — a strict allow-list of verified hawker centres, restaurants, neighbourhoods, attractions and transport facts; the model may only name list entries or world-famous landmarks.
  • Abuse damping — a sliding-window rate limit, per-visitor and site-wide, tuned to the free Agnes tier’s account-wide budget.
  • Anonymous chat log — every Q&A recorded without IPs or identifiers, declared openly on the page.
  • Honest limits — the bot doesn’t pretend to make bookings, and under peak load visitors see a polite “busy” line rather than a fake answer.

Engineering Highlights

Small site, but a few decisions carried real weight:

A key that never touches the browser

The obvious shortcut — calling the model API straight from the page — would ship the secret key to every visitor. The Pages Function exists almost entirely for this one reason: the browser talks only to its own origin, the function holds the Bearer token, and the SSE stream is passed through untouched. One moving part buys a hard security boundary.

Stopping venue hallucination with an allow-list

In QA the model would occasionally invent plausible-sounding restaurants — precisely the failure a travel guide can’t afford. Rather than hoping a softer prompt would behave, the system prompt now carries a curated verified list of real venues and a hard rule: name only list entries or world-famous landmarks. The standing policy is to extend the list when coverage feels thin, never to loosen the rule.

Honesty as a design invariant

The page declares that answers come live from Agnes AI, that AI can make mistakes, and that chats are logged anonymously. Failures render as honest error lines, and the site’s llms.txt is required to match reality — live chat, domain for sale, nothing more. These are treated as invariants of the build, not marketing copy that can drift.

The zero-config rate-limiter trade-off

Rate limiting is a per-isolate, in-memory sliding window — deliberately approximate (no KV, no Durable Objects) because the goal is abuse damping on a free-tier budget, not billing-grade precision. Naming that trade-off in the code and docs keeps a future maintainer from mistaking a conscious choice for an oversight.

Known Limits

  • The free Agnes tier allows roughly 20 answers/min account-wide — under a traffic spike some visitors will see the polite “busy” line. The upgrade path (a paid token plan, then raised limits) is documented and one config change away.
  • Rate limiting is approximate across Cloudflare’s data centres — accepted by design, see above.
