AI Lab / Two Domains, One Index

AskCarnivore.com & AskCarnivores.com

Two domains one letter apart, on purpose: a bot you ask and a portal you browse, sharing one curated index underneath. The bot routes a plain-language question to the videos that already answer it — it never writes the answer itself.

TL;DR

A switchboard for the carnivore community, built as two separate properties over one shared index. AskCarnivore.com (singular) is a bot: you ask it in words, it hands you videos. AskCarnivores.com (plural) is a portal: you browse it with your eyes, and it lists the people.

  • What — a pure router, not an explainer, plus a static human directory beside it
  • Stack — Cloudflare Pages + Pages Functions · Workers KV · Mistral Small · Google Sheets as a live override · YouTube Data API at cron time. The portal is hand-written HTML and CSS with a single script.
  • The rule that shapes everything — the model never emits a URL. It is shown ids and titles, it returns ids, and the router rebuilds every link from the index, so it cannot cite a video that does not exist.
  • Built by — solo: curation, architecture, and decisions (AI-assisted execution)
  • Status — bot live since 16 Aug 2026, answering from a 19-topic × 27-creator curation; portal live as a directory. Both carry their own “in development” strip, and the honest gaps are listed at the bottom of this page.

Two doors, one index

The singular asks the thing; the plural shows the people. That pairing is the whole product decision, and it has to be stated consistently everywhere or the two domains look like a typo of each other.

  • AskCarnivore.com — the bot. Ask in plain language, get routed to videos, cross-creator. No account, no app, no sign-up.
  • AskCarnivores.com — the portal. A bilingual directory of creators, doctors and first-person accounts, every link going straight to the source.

They share the index and nothing else. Separate repositories, separate Cloudflare Pages projects, separate secrets and analytics, no imports in either direction. Shared surfaces — the studio credit, the contact address — are copied by hand into each; the duplicate-maintenance cost is deliberate.

Why a router instead of an answer engine

The obvious build would have been an assistant that explains nutrition. This one deliberately refuses to.

  • It is finite. “Who covers what, and where” is buildable and verifiable. “Beat a frontier model at biochemistry” is not.
  • It carries less responsibility. A hub that points at people is a different liability surface from an AI that is the authority — and this subject matter makes that distinction matter.
  • A channel is not an answer. Sending someone to a YouTube channel is a second search. The index is therefore topic → video, cross-creator, not topic → channel.

So the bot returns links with neutral labels, framed as what these voices say rather than as settled fact, and it makes no treatment claims anywhere. One case is not routing at all: a personal-medical question gets a redirect to a doctor.

Architecture

[Question]
      │
      └──> (Pages Function: POST /api/ask)
                │
                ├──> Origin check ──> per-IP rate limit (KV, hashed address)
                ├──> Mistral Small  (the index rides inside a cached system prompt)
                ├──> Router: verify every id against the index, gate on intent
                └──> Links, rebuilt from the index — never from the model

  Index, in priority order:
      Cron scan ──> YouTube Data API ──> KV grid  (topic × register → videos)
      Google Sheet ──> CSV override on top of the grid
      src/index.json ──> bundled fallback when KV is empty

  askcarnivores.com ──(iframe of /embed)──> askcarnivore.com
      a window onto the bot — never a client of its worker

There is no database, no vector store and no second service. At this index size there is nothing to shard and nothing to retrieve — a decision revisited below, not one made by default.

The index has three sources, in priority order: the KV grid written by the scanner, a Google Sheet override layered on top of it, then a bundled JSON file as the fallback when KV is empty. Which one answered is reported in meta.index_source on every response, so a wrong answer can be traced to the layer that produced it.

The Sheet is fetched into KV, never from Google on the user’s clock. A stale copy is served as-is and refreshed after the response; the case being refused is a person waiting on a spreadsheet before the bot says anything.

How an answer gets built

The interesting constraint was to leave as little quality judgment as possible in the machine — and none of it hidden.

  • Topic — the model reads it from the question. This is the one thing a language model is reliably good at here.
  • Depth — the user picks it with a button: Start here or Go deeper. Phrasing rarely reveals whether someone wants an introduction or a deep dive, so the bot asks instead of guessing.
  • Which video — mechanically. Within one creator on one topic, the shorter video is the “start”, the longer one the “deep”; ordering is recency-weighted views, not raw views, so an old viral clip cannot bury good recent work.
  • Which creators — the curated roster, taken hierarchically, expanding outside it only when nobody on it covers the topic.
  • Naming the label — always experience, never a treatment claim. “What people who tried this say about X”, not “how X was cured”.

The human half of the curation is the one place editorial judgment lives: a person approves which creator covers which topic; the algorithm picks which video. One approval covers everything that creator publishes on that topic, today and next year, so the curation does not rot as content appears.

Key features

  • Scan-to-grid. A cron-time scan reads the YouTube Data API and writes a pre-computed grid of topic × depth → ranked videos. At question time the answer is already written; the model only picks the box. No live search, no per-question API call — which solves quota and link rot in the same move.
  • A byte-identical system prompt. The index rides inside the prompt and is cached per isolate, keyed on the scan timestamp, so the string changes when the grid changes — once a week — and never per request. The provider’s prefix cache keeps hitting and the index is paid for once.
  • Creator-scoped questions. “Insulin by Paul Mason” filters the routed list to that person. The model hands over a name, code does the rest, and the match is anchored on the surname — the live data credits the same doctor three different ways, and a plain substring test fails on all of them.
  • Trusted sources instead of an approval gate. Each creator is scanned from their own channel plus a small set of trusted hosts, so genuine guest appearances come in and re-upload or clip channels stay out — automatically, with no judgment call.
  • One sheet, two independent projections. A column decides whether a row can be served as an answer; a different column decides whether it appears on the public Highlights page. A row can be either, both or neither: parking a video for the bot should not pull it off the page, and putting something on the page should not quietly feed it to the model.
  • Bilingual, twice over, two different ways. The portal ships parallel English and Greek URLs with hreflang alternates; the bot does it on one page with a script. The portal cannot use the second approach — its own content-security policy blocks every script on the site.

Engineering Highlights

A handful of problems that were more interesting than they first appeared:

Two rules that had to live in code, not in the prompt

The model never emits a URL: it sees ids and titles, returns ids, and the router rebuilds the links from the index — so a hallucinated citation is not a low-probability event, it is unrepresentable. And a question classified as personal-medical returns zero links from the worker regardless of what the model asked for, so the redirect to a doctor does not depend on the model behaving. Both are guarded by tests whose entire job is to keep them true.

A frame is not an integration

The portal offers the bot in a panel — as an iframe of the bot’s public page, wrapped in portal-side chrome. It never calls the bot’s worker, and the portal’s hostname is deliberately absent from the worker’s origin allow-list: inside the frame the request origin is the bot’s own, so the check passes. The day that allow-list grows a portal hostname, the two projects have been coupled. One failure mode is worth knowing by heart: adding a sandbox attribute to that iframe gives the framed page an opaque origin, the fetch arrives with a null origin, and the panel renders a flawless chat that answers 403 to every question.

Word matching has no “not”

“Sugar” is the substance; “blood sugar” is metabolic and belongs to a different topic. Whole-word matching cannot express that exception, so roughly one in eight items in the sugar box is a title that says “blood sugar”. The overlap is accepted openly and corrected with data rows rather than with special-case code — a small decision that keeps a matching layer from slowly turning into a rules engine.

A green status code proves nothing

The bot’s host falls back to its landing page for any unknown path and answers 200, so a stale or mistyped framed URL renders a page that looks fine while the content is wrong. Anything framed is verified by opening the live page and looking inside the frame. In the same spirit, the security headers of the one route rendered by a function are set in code — the platform does not apply the static header file to generated responses, and a missing frame policy fails in the worst possible direction: silently permissive.

What is not built yet

Stated plainly, because the site’s rule is that copy matches reality:

  • Nothing calls the scanner on a schedule. The scan endpoint is live and token-guarded, but the host does not run cron for this project, so an external scheduler is still the open item.
  • No RAG, no vector store — deliberately deferred until the grid outgrows the cached prompt. The curated core fits; the full catalogue would not.
  • The portal’s tools — macro calculator, electrolytes, a getting-started plan, shopping list — and the events calendar are all out of the first scope. The directory is what is live.
  • Depth tags are incomplete for part of the roster, and are being filled in from first-hand listening rather than guessed.
  • Three recently added topics answer nothing yet. A topic only exists for the bot once a video lands in it — an empty box is never advertised — so those return “no topic” until a scan or a sheet row fills them. That is the intended behaviour, not a bug.

Status

Both domains are live. The bot answers from a real curated index; the portal is a finished directory with its planned tools still ahead of it. Designed, curated, built and operated solo.
